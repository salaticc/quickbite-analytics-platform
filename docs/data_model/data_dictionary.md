# Словарь данных QuickBite

Статус — проект на ревью. Девять сущностей покрывают заказы, доставку, платежи, продуктовые события и два дизайна эксперимента. Модель предполагает зарегистрированных покупателей и один заказ в одном ресторане. Контракты метрик и проверок описаны в [связях и кейсах](relationships.md).

## Общие правила

- В таблицах ниже **NULL** означает допустимое отсутствие значения. Все прочие поля обязательны. Идентификаторы `bigint` положительные, неизменяемые, хранятся в ClickHouse как `Int64`. Nullable поля копируются как `Nullable(T)`, SQL `NULL` сохраняет своё значение.
- В PostgreSQL `timestamptz` обозначает момент времени. В зеркале ClickHouse — `DateTime64(6, 'UTC')`. Числа `integer` становятся `Int32`, текст — `String`, UUID сохраняется как `UUID`. Точность времени сохраняется в пределах поддерживаемого обеими системами диапазона. В приложении время передаётся с явным смещением.
- PostgreSQL обеспечивает PK, FK, `UNIQUE` и построчные `CHECK`. Межстрочные правила, порядок переходов и агрегатные лимиты обеспечиваются транзакциями источника и проверяются при построении витрин. Для межстрочной проверки сумм платежей источник сериализует изменения по заказу. Удаления связанных фактов ограничиваются. В ClickHouse ключи логические, уникальность и ссылочную целостность проверяет dbt.
- Ресторан и курьер представлены текущей карточкой. Поля контекста, используемые для исторических срезов, фиксируются на фактах. Статусы, успешные платежные операции, назначения вариантов и факты активации вмешательств сохраняют исходную историю. Контакты, адреса, номера карт и свободный текст из клиентских форм в аналитическую модель не входят.

## users

Карточка зарегистрированного покупателя. **Grain** — одна строка на покупателя. **Хранение** — PostgreSQL и зеркало ClickHouse. **Кейсы** — когорты, сегментация по привлечению, единица рандомизации.

| Поле | Тип | Ключ или правило |
| --- | --- | --- |
| user_id | bigint | PK |
| registered_at | timestamptz | Момент регистрации |
| acquisition_channel | text, NULL | Первый известный канал при регистрации. Из справочника значений, после фиксации неизменяем |

**Связи и целостность.** Один пользователь имеет 0…N заказов, назначений и событий. Канал `NULL` означает, что источник неизвестен. Заказы и назначения зарегистрированного пользователя не предшествуют регистрации.

## restaurants

Карточка ресторана и границы его доступности для аналитической панели. **Grain** — одна строка на ресторан. **Хранение** — PostgreSQL и зеркало ClickHouse. **Кейсы** — география доставки, построение панели DiD и описание ресторанов.

| Поле | Тип | Ключ или правило |
| --- | --- | --- |
| restaurant_id | bigint | PK |
| city_code | text | Непустой код города из утверждённого перечня |
| time_zone | text | Допустимая IANA-зона ресторана, проверяется источником |
| opened_at | timestamptz | Начало работы в QuickBite |
| closed_at | timestamptz, NULL | Момент окончательного закрытия, строго позже `opened_at` |

**Связи и целостность.** Один ресторан имеет 0…N заказов и 0…N назначений в исследования. Интервал `[opened_at, closed_at)` задаёт присутствие ресторана в сервисе. MVP предполагает один непрерывный интервал. Временные закрытия и смена часового пояса внутри исследования требуют исключения заранее по операционному журналу либо расширения модели. Для исторической панели зона фиксируется в записи исследования, для заказа — в самом заказе.

## couriers

Стабильная идентичность исполнителя доставки. **Grain** — одна строка на курьера. **Хранение** — PostgreSQL и зеркало ClickHouse. **Кейсы** — сопоставление этапов доставки с фактически забиравшим заказ курьером и анализ переназначений.

| Поле | Тип | Ключ или правило |
| --- | --- | --- |
| courier_id | bigint | PK |
| onboarded_at | timestamptz | Момент подключения к сервису |

**Связи и целостность.** Один курьер имеет 0…N записей в истории заказов. События с этим курьером не предшествуют его подключению. Тип транспорта фиксируется в событии забора. История смен и доступности курьеров не требуется для описательного разбора длительностей. Для оценки дефицита курьеров понадобятся данные о сменах.

## orders

Коммерческий заказ и снимок контекста при оформлении. **Grain** — одна строка на заказ. **Хранение** — PostgreSQL и зеркало ClickHouse. **Кейсы** — покупки, когорты и повторные заказы, обещанный срок доставки, знаменатель DiD.

| Поле | Тип | Ключ или правило |
| --- | --- | --- |
| order_id | bigint | PK |
| user_id | bigint | FK → `users.user_id` |
| restaurant_id | bigint | FK → `restaurants.restaurant_id` |
| placed_at | timestamptz | Момент оформления |
| promised_delivery_at | timestamptz, NULL | Исходное обещание пользователю, не раньше `placed_at` |
| city_code_at_order | text | Город ресторана на момент заказа |
| time_zone_at_order | text | IANA-зона ресторана на момент заказа |
| delivery_distance_m | integer, NULL | Сохранённая оценка маршрута на момент заказа, ≥ 0 |
| currency_code | text | Валюта заказа из утверждённого перечня ISO 4217 |

**Связи и целостность.** Каждый заказ связан ровно с одним пользователем и рестораном. У заказа 0…N платежных операций, статусных и продуктовых событий. Он может быть квалифицирующим для 0…N назначений в разных экспериментах. Заказ оформлен в период работы ресторана. Текущий статус и фактические этапы рассчитываются из истории. Срезы по городу, зоне и расстоянию читаются из исторического контекста заказа.

## payments

Журнал проводок по одному заказу. **Grain** — одна строка на подтверждённую операцию списания или возврата у провайдера. **Хранение** — PostgreSQL и зеркало ClickHouse. **Кейсы** — собранные деньги клиентов, возвраты и расчётная выручка платформы.

| Поле | Тип | Ключ или правило |
| --- | --- | --- |
| payment_id | bigint | PK |
| order_id | bigint | FK → `orders.order_id` |
| provider | text | Код платежного провайдера |
| provider_operation_id | text | Идемпотентный идентификатор операции у провайдера |
| operation_type | text | `capture` или `refund` |
| parent_capture_id | bigint, NULL | FK → `payments.payment_id`. Обязателен для возврата, пуст для списания |
| posted_at | timestamptz | Момент подтверждения операции |
| currency_code | text | Валюта операции, совпадает с валютой заказа |
| amount_minor | bigint | Положительная сумма операции в минимальных денежных единицах |
| platform_revenue_minor | bigint | Компонент выручки платформы из расчёта разнесения операции, от 0 до `amount_minor` |

**Связи и целостность.** Каждая проводка принадлежит одному заказу. У списания 0…N возвратов, у возврата ровно одно исходное списание того же заказа, валюты и провайдера. `UNIQUE (provider, provider_operation_id)`. Время проводки не раньше оформления, возврата — не раньше списания. Сумма возвратов и сумма сторнированных компонентов по отдельности не превосходят соответствующие суммы исходного списания. Разнесение компонента выручки фиксирует источник платежей по принятой бизнес-политике. Без разнесения публикуются только денежные поступления и возвраты. Сумма возврата хранится положительным числом, знак определяется типом операции.

## order_status_history

Журнал операционных этапов и назначения курьеров. **Grain** — одно событие истории одного заказа. **Хранение** — PostgreSQL и зеркало ClickHouse. **Кейсы** — факт доставки для когорт и A/B, длительности этапов, SLA готовности в DiD.

| Поле | Тип | Ключ или правило |
| --- | --- | --- |
| status_event_id | bigint | PK, стабильный ID при повторной отправке события |
| order_id | bigint | FK → `orders.order_id` |
| sequence_no | integer | Положительный стабильный порядок записи в рамках заказа |
| status | text | `accepted`, `courier_assigned`, `ready`, `picked_up`, `delivered` или `cancelled` |
| occurred_at | timestamptz | Время фактического события |
| recorded_at | timestamptz | Время записи источником, ≥ `occurred_at` |
| courier_id | bigint, NULL | FK → `couriers.courier_id`. Требуется на назначении и заборе, отсутствует на остальных статусах |
| transport_mode_at_pickup | text, NULL | Режим транспорта из утверждённого перечня. Допустим только на `picked_up`, пуст при неизвестном режиме |

**Связи и целостность.** `UNIQUE (order_id, sequence_no)`. Каждая запись относится к одному заказу и максимум одному курьеру. В MVP `courier_assigned` может повторяться, остальные этапы фиксируются не более одного раза. `accepted` предшествует `ready`, далее `picked_up` и `delivered`. Назначение может идти параллельно с принятием и приготовлением, но забор требует предшествующего назначения того же курьера, действовавшего в момент забора. Допустима отмена до доставки, после финального события новые операционные этапы недопустимы. Оформление задаётся `orders.placed_at`. Для событий с одинаковым `occurred_at` порядок задаёт `sequence_no`. Если время этапа неизвестно, строки этапа нет. В витрине незавершённые или не наблюдавшиеся этапы дают `NULL` и отдельный признак полноты.

## product_events

Телеметрия пользовательских действий. **Grain** — одно уникальное событие приложения. **Хранение** — ClickHouse, источник — сборщик событий. **Кейсы** — диагностическая воронка заказа и проверка факта показа в A/B.

| Поле | Тип ClickHouse | Ключ или правило |
| --- | --- | --- |
| event_id | UUID | Логический PK, создаётся один раз на действие, обязателен при повторной отправке |
| event_name | LowCardinality(String) | `app_open`, `checkout_started`, `order_placed` или `experiment_exposed` |
| occurred_at | DateTime64(6, 'UTC') | Момент действия, прошедший проверку часов клиента |
| ingested_at | DateTime64(6, 'UTC') | Момент приёма сборщиком, сохраняется на уровне попытки доставки |
| user_id | Nullable(Int64) | Логический FK → `users.user_id`. Пуст для анонимного события |
| order_id | Nullable(Int64) | Логический FK → `orders.order_id`. Обязателен для `order_placed` |
| experiment_code | Nullable(String) | Код эксперимента, обязателен для `experiment_exposed` и пуст на остальных событиях |
| variant_seen | Nullable(String) | Фактически показанный вариант, обязателен для `experiment_exposed` и пуст на остальных |

**Связи и целостность.** У события 0…1 пользователя, заказа и назначения. Для `order_placed` требуется `user_id`, он должен совпасть с владельцем заказа. Для `experiment_exposed` требуется пользователь, `(experiment_code, user_id)` ссылается на логический ключ назначения. Проверка времени показа и соответствия варианта является диагностикой эксперимента. До прихода родительских записей события остаются в landing-слое. Дубликаты с тем же ID обязаны совпадать по бизнес-полям, иначе запись уходит на разбор.

## experiment_assignments

Назначение варианта после первого доставленного заказа. **Grain** — одна строка на пользователя в одной волне эксперимента. **Хранение** — PostgreSQL и зеркало ClickHouse. **Кейсы** — ITT, SRM, проверка показа и атрибуция повторного заказа.

| Поле | Тип | Ключ или правило |
| --- | --- | --- |
| experiment_code | text | Часть PK, уникальный код волны из версионируемого протокола |
| user_id | bigint | Часть PK, FK → `users.user_id` |
| variant | text | `control` или `treatment` по протоколу |
| assigned_at | timestamptz | Момент рандомизации |
| qualifying_order_id | bigint | FK → `orders.order_id`. Первый доставленный заказ пользователя |

**Связи и целостность.** PK `(experiment_code, user_id)`. Каждое назначение связано с одним пользователем и одним исходным заказом, у него 0…N событий показа. Источник проверяет совпадение пользователя в заказе и факт доставки не позднее рандомизации. Вариант, момент назначения и квалифицирующий заказ неизменяемы. Источник проверяет право на участие до рандомизации. Аналитический SRM диагностируется на всех назначениях, независимо от показа и результатов.

## restaurant_interventions

Зафиксированный состав пилотных и контрольных ресторанов в исследовании пропускной способности. **Grain** — один ресторан в одном исследовании. **Хранение** — PostgreSQL и зеркало ClickHouse. **Кейсы** — назначение групп, проверка соблюдения запуска и построение панели DiD.

| Поле | Тип | Ключ или правило |
| --- | --- | --- |
| study_code | text | Часть PK, код исследования из версионируемого протокола |
| restaurant_id | bigint | Часть PK, FK → `restaurants.restaurant_id` |
| study_group | text | `treatment` или `control` |
| enrolled_at | timestamptz | Момент фиксации участия до начала окна наблюдения |
| comparison_start_on | date | Зафиксированная календарная дата разделения pre/post для обеих групп |
| study_time_zone | text | IANA-зона ресторана на момент фиксации участия |
| actual_started_at | timestamptz, NULL | Фактическая активация у treatment. У control всегда `NULL` |

**Связи и целостность.** PK `(study_code, restaurant_id)`. Ровно один ресторан на строку. Группа, зона и дата сравнения фиксируются до просмотра результатов. В пределах исследования плановая дата одинакова у обеих групп. Фактический старт у treatment единожды заполняется из операционного источника и не предшествует регистрации в исследовании. `NULL` у treatment означает отсутствие подтверждённого запуска на момент среза. Пересекающиеся пилоты на тех же ресторанах проверяются по календарям протоколов до анализа. Параметры вмешательства, ожидаемые даты и окна хранятся в версионируемом протоколе исследования.
